## 1. Состав слоя синхронизации

| Файл | Ответственность |
|------|-----------------|
| `sync/VersionHash.kt` | канонический JSON, `version_hash`, формат времени UTC, номер версии протокола |
| `sync/SecureTokenStore.kt` | `device_id` / `device_token` под ключом Android Keystore |
| `sync/TlsFingerprint.kt` | пиннинг самоподписанного сертификата ПК по SHA-256 |
| `sync/RubezhSyncClient.kt` | HTTPS-вызовы `health` / `pair` / `push` / `pull` / `ack`, коды ошибок |
| `sync/PackageEngine.kt` | сборка исходящих пакетов, причинный порядок, применение входящих, конфликты |
| `sync/SyncCoordinator.kt` | сценарии для экранов: сопряжение, отправка, приём, расхождения, напоминания |
| `data/PlannerRepository.kt` | журнал операций, «надгробия», хеши, применение полезной нагрузки |
| `screens/SyncScreens.kt` | экраны «Синхронизация с ПК», «Инструкция», «Расхождения» |

Сборка зависимостей — в `AppContainer` (`MarsApplication.kt`): один `SecureTokenStore`, один `PackageEngine`,
один `RubezhSyncClient` с адресом ПК из сохранённых данных сопряжения, один `SyncCoordinator` для экранов.

## 2. Ресурсы протокола

| Путь | Назначение | Авторизация |
|------|------------|-------------|
| `GET /v1/health` | проверка связи, номер версии протокола ПК | `Bearer device_token` |
| `POST /v1/pair/request` | заявка на сопряжение по одноразовому токену из QR | без токена |
| `GET /v1/pair/status?request_id=…` | опрос подтверждения заявки на ПК | без токена |
| `POST /v1/packages/push` | отправка пакета операций телефона | `Bearer device_token` |
| `POST /v1/packages/pull` | получение пакетов, опубликованных ПК | `Bearer device_token` |
| `POST /v1/packages/ack` | подтверждение применения принятого пакета | `Bearer device_token` |

Тело запроса и ответа — JSON. Успех определяется HTTP-кодом и полем `ok`.
Ошибку ПК передаёт полем `error` с кодом протокола; при отсутствии кода он выводится из HTTP-статуса
(`401 → unauthorized`, `403 → forbidden`, `404 → not_found`, `409 → package_rejected`,
`413 → request_too_large`, `429 → rate_limited`, `503 → sync_disabled`).
Все коды и их русские формулировки — в `SyncErrorCodes`.

## 3. Сопряжение (pair)

1. На ПК: «Рубеж» → «Синхронизация» → «Показать QR-код».
2. Телефон сканирует QR. Полезная нагрузка — JSON с полями `protocol_version`, `host`, `port`, `token`, `cert_sha256`.
   Разбор — `PairingQr.parse`: проверяются версия протокола (иначе `unsupported_protocol`),
   непустой хост, непустой одноразовый токен, порт в диапазоне `1..65535` и корректность отпечатка
   (ровно 64 шестнадцатеричных символа, иначе `local_bad_qr`).
   Отпечаток приводится к нижнему регистру без `:`, `-` и пробелов.
3. Телефон строит `SyncEndpoint` из QR и **сразу** закрепляет сертификат: соединение поднимается
   только к сертификату с ожидаемым SHA-256. Одноразовый токен уходит в `POST /v1/pair/request`
   уже по закреплённому каналу вместе с именем устройства (`deviceDisplayName()`).
4. ПК возвращает `request_id`; телефон переходит в состояние ожидания и опрашивает
   `GET /v1/pair/status` раз в 3 секунды (плюс кнопка «Проверить сейчас»).
5. Человек подтверждает заявку на ПК. В ответе появляются `device_id` и постоянный `device_token`.
6. Телефон сохраняет пару в `SecureTokenStore`, а в настройки пишет несекретные данные:
   `syncPaired`, `pairedHost`, `pairedPort`, `certSha256`, `pairedDeviceName`, `deviceId`.

Одноразовый токен и данные QR живут **только в памяти** (`@Volatile pendingQr`) и не сохраняются на диск.
Отказы `pairing_denied`, `pairing_token_expired`, `pairing_token_used`, `bad_pairing_token`
сбрасывают заявку — требуется новый QR.

«Разорвать сопряжение» удаляет `device_id` и `device_token`, очищает адрес и отпечаток в настройках,
локальные задачи и проекты при этом **остаются**.

## 4. Журнал операций и версии записей

Любое локальное изменение недемонстрационной записи порождает операцию журнала
(`sync_operations`) со полями протокола: `operation_id`, `entity_type`, `entity_uuid`,
`op`, `base_hash`, `new_hash`, `payload`, `device_id`, `protocol_version`.
Удаление дополнительно создаёт «надгробие» (`sync_tombstones`) с `base_hash` удалённой версии.

Версия записи — `version_hash`: SHA-256 канонического JSON полезной нагрузки.
Канонизация (`VersionHash.canonicalJson`): ключи отсортированы, разделители без пробелов,
`null` печатается как `null`, целые числа без дробной части, строки экранируются по правилам JSON,
не-ASCII символы остаются как есть (UTF-8, без `\uXXXX`). Это соответствует
`json.dumps(payload, sort_keys=True, separators=(',', ':'), ensure_ascii=False)` на стороне ПК.

Набор полей полезной нагрузки фиксирован:

- проект: `archived`, `created_at`, `description`, `entity_type = "project"`, `name`, `sync_uuid`;
- задача: `created_at`, `description`, `due_at`, `entity_type = "task"`, `priority`, `project_uuid`, `status`, `sync_uuid`, `title`.

Время для `created_at` и `due_at` входит в хеш **как строка**.
Правило corr1:
- входящие строки с ПК сохраняются без нормализации (`+00:00` не превращается в `Z`);
- микросекунды, пришедшие с ПК, сохраняются в исходной строке без потери;
- локально Android печатает UTC в Python-совместимом виде: `+00:00`, без дробной части при `000000`,
  и с ровно 6 цифрами при ненулевых микросекундах (`.123000+00:00`);
- `updated_at` в хеш не входит.

Эталонные векторы канонизации и хешей закреплены тестом
`app/src/test/java/com/mars/planner/VersionHashParityTest.kt`.

## 5. Сборка исходящего пакета (push)

`PackageEngine.buildOutgoingPackage`:

1. Требуется сопряжение: пустой `device_id` — отказ `local_not_paired`.
2. Берутся неподтверждённые операции журнала. Если их нет — отправлять нечего.
3. `device_id` каждой операции подставляется равным устройству Bearer-токена
   (ПК отклоняет пакет с кодом `sender_mismatch` при расхождении).
4. `CausalOrder.order` строит устойчивый топологический порядок:
   - операции одной сущности сохраняют исходную последовательность,
   - `task:create` / `task:update` со ссылкой на проект идут после `project:create` этого проекта из того же пакета,
   - среди готовых выбирается операция с наименьшим исходным индексом,
   - цикл или неразрешимый порядок — `unresolved_dependency`.
5. `CausalOrder.trimToWireLimit` берёт **префикс** порядка, укладывающийся в предел размера.
   Префикс замкнут по зависимостям, поэтому обрезанный пакет остаётся применимым;
   остаток уйдёт следующей отправкой. Если не проходит даже одна операция — `request_too_large`.
6. `package_id` детерминирован: `SyncPackage.packageIdFor(sender, operationIds, attempt)` —
   UUID из SHA-256 строки `rubezh-package|v1|‹sender›|‹attempt›|‹operation_id,…›`.
   Повторная отправка того же набора даёт **тот же** `package_id`, и ПК распознаёт дубль как идемпотентный.

После ответа `ok` операции помечаются подтверждёнными (`PackageEngine.onPushAccepted` → `ackOperations`),
номер попытки сбрасывается, в настройки пишется `lastPushAt`.
Ответ `package_rejected` увеличивает счётчик попытки, чтобы следующий пакет получил **новый** `package_id`.

## 6. Приём и применение (pull, ack)

`SyncCoordinator.pullChanges` → `RubezhSyncClient.pullPackages` → `PackageEngine.applyIncomingPackage`
для каждого пакета → `RubezhSyncClient.ackPackage`.

Применение (`applyIncomingPackage`):

1. Пустой `package_id` — отказ `invalid_payload`.
2. Пакет с известным `package_id` не применяется повторно: ранее применённый даёт `AlreadyApplied`
   (телефон всё равно посылает `ack`), ранее отклонённый — `package_rejected`.
3. Проверки до записи: версия протокола, непустой `sender_device_id`,
   совпадение `device_id` операций с отправителем, наличие `payload` у всех операций кроме `delete`.
4. Все записи идут **одной транзакцией** (`PlannerRepository.withTxn`); исключение проверки
   откатывает пакет целиком и помечает `package_id` отклонённым.
5. Планировщик применения устойчив по исходным индексам: задача со ссылкой на ещё не созданный
   проект откладывается и повторяется после его создания; неразрешимая ссылка — `unresolved_dependency`.
6. Каждая применённая удалённая операция записывается в журнал как уже подтверждённая,
   поэтому повтор того же `operation_id` идемпотентен и не уходит обратно на ПК.

Решение по одной операции (`applyOne`), где `localHash` — версия записи на телефоне:

| Операция | Условие | Результат |
|----------|---------|-----------|
| `create` | локальной записи нет, «надгробия» нет | запись создаётся |
| `create` | `localHash == new_hash` | пропуск (уже применено) |
| `create` | запись есть или есть «надгробие» | **конфликт** |
| `update` | локальной записи нет и «надгробия» нет | запись создаётся |
| `update` | `localHash == new_hash` | пропуск |
| `update` | `localHash == base_hash` | запись обновляется |
| `update` | локально удалено («надгробие») | **конфликт** (удаление против изменения) |
| `update` | иное расхождение хешей | **конфликт** |
| `delete` | локальной записи нет | пропуск |
| `delete` | `localHash` равен `base_hash` или `new_hash` | запись удаляется |
| `delete` | иное расхождение | **конфликт** |

Итог применения — счётчики `added` / `updated` / `deleted` / `conflicts` / `skipped`,
из которых собирается сообщение экрана «Получено с ПК: новых …, обновлено …, удалено …».
После приёма напоминания перепланируются по срокам открытых задач; в настройки пишется `lastPullAt`.

## 7. Расхождения

Конфликт **никогда не затирает** локальные данные: обе версии сохраняются в `sync_conflicts`
(канонический JSON локальной и удалённой версии, коды операций, `package_id`, время обнаружения).
Удаление на одной стороне отражается объектом `{"deleted":true,…}`.

Экран «Расхождения» показывает обе версии человекочитаемо и предлагает выбор:

- «Оставить телефон» — расхождение закрывается, локальная запись не меняется;
- «Принять ПК» — применяется удалённая версия (для `delete` — удаление), затем перепланируются напоминания.

Пока есть незакрытые расхождения, в настройки пишется код `conflict_state`, а на экранах виден счётчик.

## 8. Ограничения и предохранители клиента

- Тайм-ауты: соединение 8 с, чтение и запись 20 с, весь вызов 45 с; автоповтор соединения выключен.
- Ответ больше 1 MiB отбрасывается с кодом `local_response_too_large` (читается не более лимита + 1 байт).
- Тело запроса больше 1 MiB не отправляется (`request_too_large`).
- Ошибка TLS различается: несовпадение отпечатка — `local_tls_pin_mismatch`, прочие — `local_tls_error`.
- Недоступность сети — `local_network_unavailable`, тайм-аут — `local_timeout`.
- Код последней ошибки хранится в настройках (`lastSyncError`) и показывается на экране по-русски.
- Демонстрационные записи не порождают операций и на ПК не уходят.
