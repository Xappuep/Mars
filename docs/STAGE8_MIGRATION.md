# Этап 8 — перенос данных Mars 1.x в модель «Рубежа»

**Статус: этап 8 реализован, ожидает технической и ручной приёмки.**
Не принят и не опубликован.

| Параметр | Значение |
|----------|----------|
| Схема Room | была **1**, стала **3** |
| Миграция | `MarsMigrations.MIGRATION_1_2` + `MarsMigrations.MIGRATION_2_3` (`app/src/main/java/com/mars/planner/data/db/MarsMigrations.kt`) |
| Импорт резервных копий | `BackupCodec.toModels` (`app/src/main/java/com/mars/planner/export/BackupCodec.kt`), `BACKUP_FORMAT_VERSION = 2` |
| Версия приложения | `2.0.0` (`versionCode 3`) |

Перенос выполняется в двух местах и по одинаковым правилам:

1. **База на устройстве** — при первом запуске 2.0.0 поверх 1.x (Room 1 → 2 → 3).
2. **Резервная копия JSON** — при импорте файла, созданного в Mars 1.x.

Миграция базы выполняется внутри транзакции Room: либо применяется целиком, либо не применяется вовсе.
Повторный запуск невозможен — после успешного применения версия схемы уже равна 3.

## Правила переноса

### 1. Категории → проекты

Каждое непустое значение поля `category` недемонстрационной задачи становится **проектом**:

- имя проекта — текст категории после обрезки пробелов;
- описание проекта — пустая строка, `archived = 0`;
- одинаковые категории дают **один** проект (сопоставление по имени);
- задачи получают ссылку `projectSyncUuid` на проект своей категории;
- пустая категория — задача остаётся **без проекта** (`projectSyncUuid = NULL`).

При импорте копии применяется то же правило: проект ищется по имени среди уже перенесённых, при отсутствии — создаётся.

### 2. Подзадачи → задачи с пометкой

Вложенность в модели «Рубежа» отсутствует. Каждая подзадача становится **самостоятельной задачей**.
Связь с родителем сохраняется текстом в описании:

```
Ранее подзадача задачи «‹заголовок родителя›».
```

- если описание было непустым, пометка добавляется в конец через пустую строку;
- если родитель не найден, вместо заголовка подставляется `№‹id›`;
- поля `parentTaskId` и `nestingLevel` в новую модель не переносятся (остаются только в архиве).

### 3. Дополнения → задачи с пометкой

Сущность «дополнение» (`enhancements`) удалена. Каждое дополнение становится **задачей**:

```
Ранее дополнение к задаче «‹заголовок исходной задачи›».
```

- пометка добавляется по тем же правилам, что и для подзадач;
- проект берётся от исходной задачи (её категория);
- приоритет сохраняется как есть;
- срок берётся из `plannedDateEpochDay` (дата без времени → см. правило 5);
- статус: `realized` и `cancelled` → `done`, все остальные (`idea` и прочие) → `open`;
- дополнения, привязанные к демонстрационной задаче, не переносятся.

### 4. Статусы

| Статус Mars 1.x | Статус 2.0.0 | Примечание |
|-----------------|--------------|------------|
| `NEW` | `open` | — |
| `IN_PROGRESS` | `open` | — |
| `POSTPONED` | `open` | счётчик и причина переноса не переносятся |
| `NOT_DONE` | `open` | — |
| `DONE` | `done` | — |
| `CANCELLED` | `done` | учитывается отдельно в отчёте как «отменённые» |

`CANCELLED` считается закрытым состоянием: задача переходит в `done` и попадает в внутренний архив миграции
вместе со своим исходным статусом, поэтому исходное «отменено» не теряется и восстановимо из архива.
Число таких задач показывается пользователю строкой «Отменённых задач помечено выполненными».

Программное соответствие: `TaskStatus.fromLegacyKey` (`domain/model/Enums.kt`).

### 5. Дата без времени → 23:59 местного времени

В 1.x срок хранился как `dueDateEpochDay` плюс необязательные `dueTimeMinutes`.

- время указано → `дата + время` в часовом поясе устройства;
- время **не** указано → `дата + 23:59` в часовом поясе устройства;
- даты нет → срок пустой (`NULL`).

Пересчёт выполняется через `ZoneId.systemDefault()`, результат сохраняется в миллисекундах эпохи.
Количество задач, которым назначено `23:59`, показывается в отчёте строкой «Задач со сроком на 23:59».

### 6. Демо-данные исключены из обмена

- Демонстрационные записи переносятся в новые таблицы с флагом `isDemo = 1`.
- Категории демо-задач **не** превращаются в проекты.
- Дополнения демо-задач **не** переносятся.
- Записи с `isDemo = 1` не порождают операций журнала синхронизации, поэтому на ПК не уходят.
- ПК со своей стороны отвечает кодом `demo_not_allowed`, если открыта демо-база; локальные демо-данные удаляются в Настройках.

### 7. Назначение UUID

- Каждому проекту и каждой задаче назначается `syncUuid` — случайный UUID версии 4.
- Числовые `id` из 1.x в новой модели служебные и в обмене не участвуют.
- `syncUuid` уникален (уникальный индекс в таблицах `projects` и `tasks`) и служит единственным идентификатором сущности в протоколе (`sync_uuid`, `entity_uuid`).
- При импорте копии формата 2 существующие `syncUuid` сохраняются; при импорте копии 1.x или при пустом значении UUID генерируется.

### 8. Внутренний архив старых данных

Перед удалением старых таблиц их содержимое целиком сохраняется в таблицу `migration_archive`:

- `archiveJson` — все строки `tasks` и `enhancements` версии 1 в исходном виде (включая `postponeCount`, `postponeReason`, `parentTaskId`, `nestingLevel`, `relatedToTaskId`, исходный `status`) плюс `schemaVersion = 1`;
- `reportJson` — счётчики переноса: `projectsCreated`, `tasksMigrated`, `subtasksConverted`, `enhancementsConverted`, `cancelledToDone`, `dueAt2359Count`;
- `reportShown` — признак, что отчёт уже показан пользователю.

Архив **внутренний**: он лежит в базе приложения, наружу автоматически не выгружается,
идентифицируется как `internal:migration_archive#‹id›`.
Выгрузить его файлом можно вручную: **Настройки → «Архив миграции»**.
После записи архива старые таблицы `tasks_v1_legacy` и `enhancements_v1_legacy` удаляются.

## Отчёт пользователю

При первом запуске после миграции показывается однократный диалог «Данные перенесены в новую модель» со счётчиками:

- создано проектов из категорий;
- перенесено задач;
- подзадач стали отдельными задачами;
- дополнений стали задачами;
- отменённых задач помечено выполненными;
- задач со сроком на 23:59.

Признак показа хранится в `migration_archive.reportShown`, повторно диалог не появляется.

## Что не переносится в новую модель

| Поле 1.x | Судьба |
|----------|--------|
| `postponeCount`, `postponeReason` | только в архиве |
| `parentTaskId`, `nestingLevel` | только в архиве, связь отражена текстом в описании |
| `relatedToTaskId` | только в архиве |
| `reminderAtEpochMillis` | напоминания перепланируются заново по срокам открытых задач |
| `enhancements.deferredReason`, `convertedTaskId` | только в архиве |
| настройки `syncHost`, `syncPort`, `syncKey` | больше не читаются приложением; актуальные `pairedHost`, `pairedPort`, `certSha256` приходят из QR |
